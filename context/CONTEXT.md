# idea-finder — концепция

## Цель
Система ищет в интернете боли пользователей, оценивает их с учётом реалий рынка РФ
и показывает в дашборде для выбора идеи под реализацию.

## Решения (обсуждено 2026-09-17)
- Источники: сначала утверждённый реестр площадок с лёгким доступом (RSS/API/простой HTML); поисковый API — второй эшелон (discovery длинного хвоста). Волна 1: FL.ru/Freelance.ru/Habr Freelance/Weblancer (RSS, freelance-спрос), Habr (RSS), Google Play отзывы RU (google-play-scraper, без ключа), Otzovik/iRecommend, Otvet Mail.ru, форумы, RuStore отзывы, Telegram/Telethon. Волна 2: Kwork (каталог), Дзен, Ozon/WB, YouDo/Profi, YouTube.
- Тип сигнала: RawPost.kind = demand | complaint | discussion. Заказ с биржи (demand) — прямое доказательство платёжеспособного спроса, усиливает монетизируемость в скоринге.
- LLM: извлечение болей и скоринг. Несколько провайдеров, настройка в дашборде (страница «Настройки LLM»): таблица llm_provider (name, base_url, api_key маскирован, model, enabled, is_default), переключение active-провайдера кликом. LlmClient factory строит клиент по active. FakeLlmClient — провайдер kind=fake (детерминированный мок из фикстур); мок-режим = is_default на fake, реальный ключ добавится через UI без кода. Локальный GPU не тянем (8GB VRAM).
- Fetch-слой: httpx (async, рейт-лимиты per-domain, robots.txt) → trafilatura (экстракция текста, fallback selectolax) → Playwright только для JS-доменов (триггер — подозрительно короткий текст). Не Scrapy (обход мелкий), не crawl4ai (тяжёлый).
- Капчи: профилактика (API вместо скрейпа выдачи, рейт-лимиты, cookie-сессии) → graded-реакция (cooldown домена → пометка blocked в дашборде → ручное решение через Playwright headed с сохранением кук). Сервисы-решалки и прокси-пулы не используем.
- Firecrawl self-hosted рассмотрен, отклонён: Docker-стек 8-12GB RAM, антибот/прокси/поиск — только в платном облаке. Fetch-слой абстрагирован интерфейсом Fetcher (fetch(url)->text) — при необходимости подцепить Firecrawl-адаптер дёшево.
- Стек: Python. Хранилище: PostgreSQL embedded через pgserver (unix-сокет, без TCP-портов; pgvector из коробки — эмбеддинги кластеризации в той же БД). Дашборд: Streamlit (таблица кластеров, фильтры, цитаты; кнопка «Прогнать сбор» = subprocess + статус из БД; fallback при застревании — NiceGUI).
- Запуск: по запросу владельца (CLI/кнопка «Прогнать сбор»), без планировщика.
- MVP: три адаптера end-to-end (FL.ru RSS + Habr RSS + Google Play отзывы RU — три типа доступа), полный пайплайн до дашборда; далее конвейерное добавление источников.
- Валидация спроса: Яндекс Wordstat (бесплатный API, ~1000 req/сут) — post-MVP задача после G1. Кластер → LLM генерирует поисковые фразы боли → частотность Wordstat → таблица wordstat_query (кэш, ревалидация ~неделя) → сигнал «поисковый спрос подтверждён» в скоринг + показ в карточке кластера. Триангуляция сигналов: жалобы (пайплайн) + платёжеспособность (demand-биржи) + поисковый спрос (Wordstat). Второй эшелон: массовый поиск идей словами-магнитами («не работает», «жалею») × категории → обратный поиск обсуждений. Нужен Yandex-аккаунт владельца.

## Пайплайн
Источники → RawPost{source,url,title,text,date} → LLM-извлечение боли
→ эмбеддинги + кластеризация (дедуп, частота = сигнал) → скоринг по рубрике РФ-рынка
→ PostgreSQL (pgserver) → дашборд (кластеры, отсортированные по скору, цитаты-доказательства, ссылки).

## Рубрика скоринга (рынок РФ)
частота/разброс источников, свежесть, платёжеспособность аудитории, конкуренция,
монетизируемость, регуляторные риски, сложность MVP → взвешенный скор + обоснование.

## Ограничения
- Антибот vc.ru/Дзен/Ozon — не парсить напрямую; только RSS/каталоги волны 2, тяжёлые — через поисковый API второго эшелона.
- LLM-вызовы: бюджет-контроль (лог расходов на прогон).
- Юридика: robots.txt, рейт-лимиты, официальные API где есть.

## Дефолты по дырам (2026-09-17, возражения → правка)
- Эмбеддинги: multilingual-e5-small локально CPU (не LLM API).
- Идемпотентность: canonical URL (срез utm), unique-констрейнт, refetch только новых URL; инкрементальность через RSS-курсоры/пагинацию/даты.
- Репо: git init, .gitignore (.env, data/, .orenda/, .omp/), uv + ruff + ty (типы, уже установлен v0.0.9). Секреты: LLM-ключи хранятся в БД (llm_provider.api_key, в UI маскируются), БД и .env в gitignored data/.env путях.
- LLM-регрессия: фикстурный датасет 20-30 размеченных постов для проверки промптов.
- MVP-приёмка: прогон по трём MVP-источникам → кластеры с цитатами, скором и типом сигнала в дашборде (числа зафиксировать при постановке).
- Реестр источников (таблица source: тип доступа, статус, рейт-лимиты) — отдельная сущность; новый источник = новый адаптер по контракту, без изменения пайплайна.
- Фидбек-петля: кнопки «интересно/скрыть» на кластере в дашборде (фильтр, данные на будущее).

## System design (2026-09-17)
Модульный монолит, batch-ETL, ports & adapters на стыках изменчивости.
- Стадии collect→extract→cluster→score — идемпотентные функции над таблицами; прогресс в таблице run; перезапуск стадии безопасен.
- Протоколы: SourceAdapter (fetch_new(since)->[RawPost]), Fetcher, LlmClient. Новый источник = новый адаптер.
- Две точки входа: CLI (стадии + полный прогон) и Streamlit (чтение + subprocess прогона). Streamlit в пайплайн не лезет.
- Записи в БД только через db/repo.py; стадии связаны таблицами, не вызовами. ty strict в core/ и db/.
- Нет: Celery/очереди, REST между компонентами, Docker, микросервисы.
- Структура: sources/ fetch/ llm/ core/ db/ web/ cli.py fixtures/.

## Промпты и их версионирование (2026-09-17)
Три уровня: файлы llm/prompts/*.md (Jinja2) в git — базовые; таблица prompt_version(name, version, body, source=file|ui) в БД — активные, история, откат (в т.ч. к файловой); привязка prompt_version_id в run/score — воспроизводимость и сравнение версий.
UI-страница «Промпты»: редактирование (сохранение = новая версия), история с диффами, кнопка «Прогнать регрессию» (фикстуры, дельта vs прошлый прогон), перегон кластеров новой версией со сравнением скоров.

## Контроль качества (2026-09-17)
Счётчики брака на каждом стыке, пишутся в run: сбор (новые/дубли/ошибки по источнику, валидация входа), экстракция (длина текста, suspect_short, доля fallback'ов), LLM (доля невалидного JSON; анти-галлюцинация: цитата обязана строкой быть в исходном тексте, иначе брак), кластеризация (распределение размеров, доля синглтонов), скоринг (контроль распределения, обоснование обязательно).
Человеческие проверки: страница «Источники» (health), «Сырьё» (семплы экстракции), семплы «пост→боль», кнопки калибровки на кластере. Страница «Здоровье системы»: история прогонов, стоимость LLM, доли брака, тренды.

## Самообучение (2026-09-17)
v1 — нет: пайплайн детерминированный, калибровки human-in-the-loop. Копим сырьё: фидбек кластеров, метки сплитов, версии промптов+скоры, health источников.
Post-MVP петли (по нарастающей, каждая через кнопку «применить»): калибровка весов скоринга логрегом по фидбеку → веса источников по принятым кластерам → порог кластеризации по сплитам (с регрессией).
Не делаем: автоправку промптов LLM'ом, онлайн-переобучение эмбеддингов.

Git-модель: main (интеграционная, мерж --no-ff владельцем) + task-<N>-<slug> worktree на задачу; dev сознательно нет (≤2 воркеров). Ремоут: https://github.com/ramgml/idea-finder — ПУБЛИЧНЫЙ (создан 2026-09-17, main запушен); правило публичности: секреты только в gitignored путях/БД, утечка = немедленная ротация; хуки появятся с Makefile (A1). .omp/ORCHESTRATOR.md + .omp/agents/pm.md — роли оркестратора и PM.
